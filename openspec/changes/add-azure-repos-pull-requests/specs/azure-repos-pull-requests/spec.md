## ADDED Requirements

### Requirement: Azure Repos pull requests use the connected account's token
In-app pull request features for an Azure Repos remote SHALL authenticate with the personal access token saved on this Mac for the connected Azure Repos account whose organization matches the remote, whether that account currently uses HTTPS or SSH. When no matching account has a saved token, the Pull Requests view SHALL offer "Connect Account" or "Reconnect", as it does for GitHub and GitLab.

#### Scenario: HTTPS account connected
- **WHEN** the user opens Pull Requests for a repository whose remote is `https://dev.azure.com/Trantienthanh1998/ChatApp/_git/ChatApp` and an Azure Repos account for `Trantienthanh1998` with a saved token is connected
- **THEN** the pull request list loads with that account's token

#### Scenario: SSH account with a kept token
- **WHEN** the matching Azure Repos account uses SSH and still has the personal access token saved from an earlier HTTPS connection
- **THEN** the pull request list loads with that token

#### Scenario: No usable account
- **WHEN** no Azure Repos account for the remote's organization is connected, or the only matching account has no saved token
- **THEN** the Pull Requests view shows the connect or reconnect action instead of a list

### Requirement: Azure pull requests are listed with the existing filters
The Pull Requests view SHALL list the repository's Azure pull requests, newest first, 30 per page, with previous and next paging. Azure statuses SHALL map to app states as follows:
- An active pull request is Open, or Draft when it is marked as a draft.
- A completed pull request is Merged.
- An abandoned pull request is Closed.

#### Scenario: Open filter
- **WHEN** the repository has one active pull request, one draft, one completed, and one abandoned, and the user selects Open
- **THEN** the active and draft pull requests are listed and the draft is marked as a draft

#### Scenario: Closed filter
- **WHEN** the user selects Closed
- **THEN** the completed pull request is listed as merged and the abandoned one as closed

#### Scenario: Next page
- **WHEN** the repository has more than 30 pull requests matching the filter
- **THEN** the next-page action is enabled and loads the following pull requests

### Requirement: Azure pull request filters match the app's states
The Open filter SHALL show only open and draft Azure pull requests, the Closed filter only merged and closed ones, and the All filter all of them. "Created by me" SHALL show only pull requests created by the connected account's user.

#### Scenario: Created by me
- **WHEN** the user turns on "Created by me"
- **THEN** only pull requests created by the connected Azure account's user are listed

### Requirement: Azure pull request rows show merge readiness
Each Azure pull request row SHALL show its title, number, author, source and target branches, and merge readiness:
- Ready when Azure reports the merge as succeeded.
- Blocked when it reports conflicts, a policy rejection, or a failure.
- Unknown otherwise.

#### Scenario: Pull request with conflicts
- **WHEN** Azure reports merge conflicts for an active pull request
- **THEN** its row shows that it is blocked

### Requirement: Credentials stay out of pull request output
The Azure personal access token SHALL NOT appear in logs, error messages, or Repository AI context.

#### Scenario: Request fails
- **WHEN** an Azure pull request request fails
- **THEN** the error shown to the user contains neither the token nor the authorization header

### Requirement: The open pull request for a branch is found
Looking up the pull request for a branch SHALL return the active pull request whose source branch is that branch. When there is none, it SHALL return the most recently created completed or abandoned one, and otherwise none.

#### Scenario: Branch with an active pull request
- **WHEN** branch `feature/login` has an active pull request into `main`
- **THEN** the branch's pull request action opens that pull request

#### Scenario: Branch without a pull request
- **WHEN** no pull request uses `feature/new` as its source branch
- **THEN** the lookup returns none and the branch offers to create a pull request

### Requirement: Azure pull request detail shows the description, reviewers, and comments
Opening an Azure pull request SHALL show:
- Its title, state, author, branches, and description.
- Its reviewers with their names.
- Its text comments in creation order.

Comments generated by Azure DevOps, such as vote changes, pushes, and policy updates, SHALL NOT be shown, and neither SHALL deleted comments. A comment attached to a file SHALL show its file path and line. Opening the pull request in the browser SHALL open its Azure web page.

#### Scenario: Conversation with system activity
- **WHEN** a pull request has two user comments and several vote and push updates
- **THEN** only the two user comments are shown

#### Scenario: File comment
- **WHEN** a reviewer commented on line 12 of `Sources/App.swift`
- **THEN** that comment shows the path `Sources/App.swift` and line 12

#### Scenario: Open in browser
- **WHEN** the user opens pull request 42 in the browser
- **THEN** `https://dev.azure.com/{org}/{project}/_git/{repo}/pullrequest/42` opens

### Requirement: Azure pull request changes can be viewed as diffs
The Changes tab SHALL list every file changed in the pull request's latest iteration, compared with the common base commit, with its status (added, modified, deleted, or renamed) and, for renames, its previous path. For each text file, the tab SHALL show a unified diff with three lines of context.

#### Scenario: Modified text file
- **WHEN** the pull request modifies `README.md`
- **THEN** the Changes tab lists `README.md` as modified and shows its diff

#### Scenario: Renamed file
- **WHEN** the pull request renames `old.txt` to `new.txt` and changes one line
- **THEN** the file is listed as renamed from `old.txt` and its diff shows the changed line

### Requirement: Large and binary Azure diffs are skipped with a reason
A changed file SHALL show its listed status and a reason instead of a diff in these cases:
- It is binary.
- Either version is larger than 1 MB.
- It is beyond the first 100 files of the pull request.

The reason SHALL say that the diff is available on Azure DevOps.

#### Scenario: Binary file
- **WHEN** the pull request adds `logo.png`
- **THEN** the file is listed as added with a reason instead of a diff

#### Scenario: Very large pull request
- **WHEN** the pull request changes 150 text files
- **THEN** all 150 files are listed, the first 100 show diffs, and the rest show a reason

### Requirement: Comments can be added to Azure pull requests
Adding a comment to an Azure pull request SHALL post it as a new active comment thread and refresh the conversation, so the new comment appears.

#### Scenario: Add a comment
- **WHEN** the user writes "Looks good" on pull request 42 and submits it
- **THEN** Azure DevOps receives a new thread with that comment and the comment appears in the conversation

### Requirement: Azure pull requests can be merged
Merging an Azure pull request SHALL complete it with a merge commit and SHALL keep the source branch. A successful merge SHALL refresh the pull request so it shows as merged. When Azure DevOps refuses the merge, the pull request SHALL stay open and the app SHALL show Azure's message. Reasons include unmet branch policies, missing approvals, and merge conflicts.

#### Scenario: Merge succeeds
- **WHEN** the user merges an active pull request with no blocking policies
- **THEN** the pull request is completed with a merge commit, the source branch still exists, and the pull request shows as merged

#### Scenario: Blocked by policy
- **WHEN** the target branch requires an approval that the pull request does not have
- **THEN** the merge fails with Azure's policy message and the pull request stays open

### Requirement: Azure pull requests can be created in the app
The create pull request sheet SHALL create Azure pull requests from the chosen source and target branches, title, and description, and SHALL open the created pull request. For Azure Repos, the sheet SHALL NOT show the Reviewers and Assignees pickers. Creating a pull request when one is already active for the same branches SHALL show Azure's message and SHALL NOT create a duplicate.

#### Scenario: Create a pull request
- **WHEN** the user creates a pull request from `feature/login` into `main` titled "Add login"
- **THEN** an active Azure pull request with that title is created and opened in the app

#### Scenario: Participant pickers hidden
- **WHEN** the create sheet is opened for an Azure Repos remote
- **THEN** no Reviewers or Assignees picker is shown

### Requirement: Azure errors map to actionable messages
Azure pull request requests SHALL report errors as follows:
- A token that is rejected or expired, including Azure redirecting to a sign-in page, SHALL report that the account needs to be connected again.
- A missing permission SHALL report that the token needs the "Code (Read & Write)" scope.
- A repository that was not found SHALL report that it is unavailable from the connected account.
- Any other Azure error SHALL show Azure's message when it provides one.

#### Scenario: Expired token
- **WHEN** Azure DevOps rejects the account's token while listing pull requests
- **THEN** the Pull Requests view asks the user to reconnect the account

#### Scenario: Read-only token merges
- **WHEN** the token lacks write access and the user merges a pull request
- **THEN** the error says the token needs the "Code (Read & Write)" scope

### Requirement: Azure repository visibility is resolved for plan gating
The app SHALL resolve an Azure repository as public or private from its Azure DevOps project's visibility, trying anonymously first and then with a connected account's token. A repository whose visibility cannot be resolved SHALL stay unknown. Plan gating for pull requests, Git Flow, and Git LFS SHALL use this visibility, as for GitHub and GitLab:
- Free users get these features for public Azure projects.
- Pro users get them for all Azure projects.

#### Scenario: Pro user with a private project
- **WHEN** a Pro user opens Pull Requests for a repository in a private Azure project
- **THEN** access is allowed and the list loads

#### Scenario: Free user with a private project
- **WHEN** a free user opens Pull Requests for a repository in a private Azure project
- **THEN** the Pro upgrade prompt is shown

#### Scenario: Free user with a public project
- **WHEN** a free user opens Pull Requests for a repository in a public Azure project
- **THEN** access is allowed
